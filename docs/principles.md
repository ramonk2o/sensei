# Sensei principles

Sensei's skills maintain skill plugins: they plan a new plugin, set up the repository, keep its backlog and changelog, carry each change to a skill from a real case to a merge, and release versions. This file holds the principles every sensei skill follows and the questions for judging a change to sensei itself. A change that breaks a principle is a design decision and needs the maintainer's explicit agreement.

## Working with the maintainer

1. **The maintainer decides; the skill proposes.** Nothing is edited before an explicit OK to a plan, nothing is merged before an OK to the whole change, and nothing is published before an OK to the version. "OK" or "go ahead" approve; silence, a passing comment or approving a round's answers do not. Two light paths are written first and reported right after, because the request already says exactly what to write: a wording fix that changes no behavior, and a backlog entry the maintainer dictated, in BACKLOG.md or as an issue.
2. **Start from the real case.** A change answers something that happened: what a skill was asked, what it did and what it should have done. A reviewer's finding that names the text and the realistic request it breaks also counts as a case. A skill not yet built starts from concrete requests it must serve, in its users' words, with what a good result looks like. An impression ("it's off") is a reason to ask for the case, not to propose a fix.
3. **Propose before asking.** Questions come in rounds of up to five, numbered, each with a recommended answer and a one-line reason, the riskiest first. The case itself is the exception: only the maintainer has it, so the skill asks for it without proposing one, since an invented case breaks principle 2. When the repository answers a question, the skill uses that answer and says where it came from.

## Protecting the plugin

4. **Protection matches the change.** Cheap, certain checks (the script, the validator, settings) run on every change. Costly ones (review agents, evals) are scaled to the change: none for a wording fix, the cohesion review for a behavior change, the cohesion review and a trigger suite for a new description, both reviews, a cold reader and a trigger suite for a new skill.
5. **Certain beats remembered.** A rule that a script or a setting can enforce is enforced there, not left to prose in CLAUDE.md: sizes and names by the check script, trailers by the attribution setting, the maintained plugin's own skills turned off in its repo by `enabledPlugins` (except sensei's own, whose installed copy does the maintenance).
6. **Drift is the usual failure.** A change to a rule is searched for in every sibling skill and every listing (README, manifests) before it is planned, and the plan names each file that must change in the same branch.
7. **Judged outside the conversation.** Reviews and tests run in agents or processes that never saw the conversation or the plan, because a model that took part already knows what the skill was meant to say.

## Building sensei's skills

8. **One owner per fact.** The backlog and changelog formats live in `log`'s references; the maintained plugin's rules live in its own `docs/principles.md` and are read at run time, never copied into sensei; the scope map is generated by the script, never kept by hand.
9. **A lean core.** `SKILL.md` loads in full on every activation, so it holds only the flow and what every step needs, within `skill_tokens` above. What a single step or kind of change uses lives in `references/` and is loaded only then. The description stays within `description_chars` and says when to use the skill and when not to.
10. **Generic and public.** Sensei names nothing from one person's setup: no maintainer, repository or private plugin. Clashes with other plugins are found at setup time from what is installed, not from a fixed list. The only tools named are ones anyone can get: Claude Code's own CLI, Anthropic's official plugins, git and Python 3, and the remote host's CLI (such as `gh`): recommended when it's installed and signed in, never required.
11. **English inside, the user's language outside.** Everything written to a project is in English unless the user explicitly asks for another language; the conversation follows the language the user speaks.

## Judging a proposal

1. Which real case does it come from?
2. Does it change behavior, or only wording?
3. Does it conflict with a principle? If so, what should change: the proposal, the principle, or neither, as a true exception?
4. Does it fit an existing skill, or does it need a new one?
5. Does it add size, turns or approvals without a visible gain?
